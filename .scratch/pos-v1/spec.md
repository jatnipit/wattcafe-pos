# POS ร้านกาแฟ–น้ำปั่น: รับออเดอร์จาก LINE และกระดานยืนยันออเดอร์

Status: ready-for-agent

## Problem Statement

ร้านกาแฟ–น้ำปั่นร้านเดียวในหมู่บ้านรับออเดอร์ผ่านแชท LINE ทุกวัน ร้านต้องอ่านข้อความด้วยตา แปลงเป็นรายการเอง คิดราคาเอง และพิมพ์ตอบลูกค้าทีละคน งานซ้ำนี้กินเวลาตอนลูกค้าเข้าพร้อมกัน และทำให้เกิดข้อผิดพลาดเรื่องเมนู จำนวน และราคา

ระบบที่ใช้อยู่เดิมไม่มีอะไรเลย: ไม่มีที่เก็บออเดอร์ ไม่มีประวัติ ไม่มีรายงานยอดขายรายวัน และไม่มีใครรู้ว่าออเดอร์ไหนทำแล้ว ส่งแล้ว หรือยังไม่จ่ายเงิน

## Solution

เว็บ POS ขนาดเล็กที่รับข้อความจาก LINE Official Account มาแสดงบนกระดานออเดอร์ พร้อมจับคำที่ร้านตั้งราคาไว้เพื่อเสนอรายการและยอดเงิน ร้านตรวจ แก้ไข และกดยืนยันเองทุกออเดอร์ แล้วไล่สถานะจนถึงจัดส่งสำเร็จและบันทึกการชำระเงิน

ระบบ **ไม่ส่งข้อความใด ๆ ออกไปหาลูกค้า** ร้านพิมพ์ตอบผ่าน LINE OA Manager เอง และ **ไม่สร้างออเดอร์อัตโนมัติ** ระบบทำหน้าที่เป็นกล่องข้อความที่เข้าใจราคา + กระดานงาน + สมุดบัญชีอย่างง่าย

## User Stories

### รับข้อความ

1. ในฐานะลูกค้า ฉันต้องการส่งข้อความสั่งเครื่องดื่มผ่าน LINE ตามปกติ เพื่อไม่ต้องติดตั้งแอปใหม่
2. ในฐานะลูกค้า ฉันต้องการให้ข้อความที่ส่งตอนร้านปิดยังถูกบันทึกไว้ เพื่อที่ร้านจะเห็นว่าฉันสั่งอะไร
3. ในฐานะร้าน ฉันต้องการให้ทุกข้อความที่เข้ามาถูกบันทึกพร้อมผู้ส่งและเวลา เพื่อไม่ให้ข้อความหลุด
4. ในฐานะร้าน ฉันต้องการให้ webhook ที่ส่งซ้ำถูกเพิกเฉย เพื่อไม่ให้เกิดออเดอร์ซ้ำ
5. ในฐานะร้าน ฉันต้องการให้ webhook ที่ลายเซ็นไม่ถูกต้องถูกปฏิเสธ เพื่อกันคนนอกยัดออเดอร์เข้ามา
6. ในฐานะร้าน ฉันต้องการให้ระบบตอบรับ LINE ภายใน 2 วินาที เพื่อไม่ให้ LINE ตัดการเชื่อมต่อ

### จับคำและสร้างออเดอร์ร่าง

7. ในฐานะร้าน ฉันต้องการให้ระบบชี้คำที่ตั้งราคาไว้ในข้อความ เพื่อไม่ต้องพิมพ์รายการซ้ำ
8. ในฐานะร้าน ฉันต้องการให้ "โกโก้ปั่น" คิดเป็นโกโก้ 35 บวกปั่น 5 เพื่อให้ยอดตรงกับราคาที่ตั้งไว้
9. ในฐานะร้าน ฉันต้องการให้คำที่ยาวที่สุดถูกจับก่อน เพื่อไม่ให้ชื่อเมนูผสมถูกนับซ้ำสองครั้ง
10. ในฐานะร้าน ฉันต้องการให้ระบบเข้าใจจำนวนหลายรูปแบบ (2, 2 แก้ว, x2, สองแก้ว, เลขไทย) เพื่อรองรับการพิมพ์จริงของลูกค้า
11. ในฐานะร้าน ฉันต้องการให้คำที่ไม่รู้จักถูกข้ามไปโดยไม่เดา เพื่อไม่ให้ระบบสร้างรายการผิด
12. ในฐานะร้าน ฉันต้องการให้ระบบไม่เดาจำนวนที่ลูกค้าไม่ได้ระบุ เพื่อให้ร้านเป็นคนถามเอง
13. ในฐานะร้าน ฉันต้องการเพิ่มคำเรียกที่ลูกค้าใช้จริง เพื่อให้ข้อความของลูกค้าจับคู่กับเมนูได้
14. ในฐานะร้าน ฉันต้องการให้คำเรียกไม่ซ้ำกันทั้งระบบ เพื่อให้ผลการจับคำแน่นอน
15. ในฐานะร้าน ฉันต้องการให้เมนูที่ปิดขายไม่ถูกจับเป็นรายการใหม่ เพื่อไม่เสนอของที่ขายไม่ได้
16. ในฐานะร้าน ฉันต้องการเห็นข้อความต้นฉบับเต็มข้างรายการที่ระบบเสนอ เพื่อตรวจก่อนยืนยัน

### ออเดอร์ร่าง

17. ในฐานะร้าน ฉันต้องการให้ข้อความที่จับคำได้อย่างน้อยหนึ่งคำกลายเป็นออเดอร์ร่าง เพื่อมีอะไรให้ตรวจ
18. ในฐานะร้าน ฉันต้องการให้ข้อความที่จับคำไม่ได้ไปอยู่ในกล่องข้อความเข้า เพื่อให้กระดานออเดอร์ไม่เต็มไปด้วยข้อความขยะ
19. ในฐานะร้าน ฉันต้องการให้ข้อความใหม่จากลูกค้าคนเดิมภายใน 10 นาทีรวมเข้าใบเดิม เพื่อไม่ให้ลูกค้าที่พิมพ์แยกสองครั้งกลายเป็นสองออเดอร์
20. ในฐานะร้าน ฉันต้องการให้ออเดอร์ร่างที่ค้างเกิน 24 ชั่วโมงถูกปิดเป็นหมดอายุ เพื่อไม่ให้คิวรก

### ยืนยันและแก้ไข

21. ในฐานะ Staff ฉันต้องการแก้เมนู จำนวน ตัวเลือก และราคาก่อนยืนยัน เพื่อให้ออเดอร์ตรงกับที่ลูกค้าต้องการ
22. ในฐานะ Staff ฉันต้องการให้การยืนยันเก็บสำเนาชื่อเมนู ตัวเลือก และราคา เพื่อให้การแก้เมนูภายหลังไม่เปลี่ยนประวัติ
23. ในฐานะ Staff ฉันต้องการให้ระบบคำนวณยอดรวมให้ เพื่อไม่ต้องคิดเลขเอง
24. ในฐานะ Staff ฉันต้องการทิ้งออเดอร์ร่างที่ไม่ใช่ออเดอร์ได้ เพื่อไม่ให้ปนกับยอดขาย
25. ในฐานะ Staff ฉันต้องการสร้างออเดอร์เองได้ เพื่อรับออเดอร์ทางโทรศัพท์หรือหน้าร้าน
26. ในฐานะ Staff ฉันต้องการได้รับแจ้งเมื่อมีคนอื่นแก้ก่อน เพื่อไม่ทับงานกัน

### เมนูและตัวเลือก

27. ในฐานะ Super Admin ฉันต้องการเพิ่ม แก้ และลบเมนูพร้อมราคาฐาน เพื่อให้ราคาตรงปัจจุบัน
28. ในฐานะ Super Admin ฉันต้องการกำหนดกลุ่มตัวเลือกที่ใช้ร่วมหลายเมนู เพื่อไม่ต้องนิยามความหวานซ้ำทุกเครื่องดื่ม
29. ในฐานะ Super Admin ฉันต้องการกำหนดว่าตัวเลือกใดบังคับเลือกและเลือกได้กี่ค่า เพื่อควบคุมการสั่ง
30. ในฐานะ Super Admin ฉันต้องการให้ค่าตัวเลือกมีราคาบวก เพื่อคิดเงินปั่นหรือท็อปปิงได้
31. ในฐานะ Super Admin ฉันต้องการปิดเมนูทันทีเมื่อของหมด เพื่อหยุดขายโดยไม่กระทบออเดอร์เก่า
32. ในฐานะ Super Admin ฉันต้องการจัดการคำเรียกของเมนูและตัวเลือก เพื่อให้ระบบเข้าใจภาษาที่ลูกค้าใช้

### สถานะออเดอร์

33. ในฐานะ Staff ฉันต้องการเลื่อนออเดอร์ตามลำดับ รับออเดอร์ → กำลังทำ → กำลังส่ง → จัดส่งสำเร็จ เพื่อให้กระดานตรงความจริง
34. ในฐานะ Staff ฉันต้องการให้การย้อนสถานะถูกปฏิเสธ เพื่อไม่ให้ประวัติเพี้ยน
35. ในฐานะ Staff ฉันต้องการยกเลิกออเดอร์ได้ถึงขั้นกำลังทำ เพื่อแก้ความผิดพลาดหน้าร้าน
36. ในฐานะ Super Admin ฉันต้องการยกเลิกออเดอร์หลังออกส่งแล้วพร้อมเหตุผล เพื่อบันทึกกรณีพิเศษ
37. ในฐานะ Staff ฉันต้องการเห็นว่าใครเปลี่ยนสถานะเมื่อไร เพื่อตรวจย้อนหลังได้
38. ในฐานะ Staff ฉันต้องการให้กระดานอัปเดตเอง เพื่อเห็นออเดอร์ใหม่ขณะยืนอยู่หน้าเคาน์เตอร์

### ลูกค้าและที่อยู่

39. ในฐานะ Staff ฉันต้องการพิมพ์บ้านเลขที่บนหน้าจอออเดอร์ เพื่อเก็บข้อมูลจัดส่ง
40. ในฐานะ Staff ฉันต้องการให้ที่อยู่ล่าสุดของลูกค้าเดิมถูกเติมให้ เพื่อไม่ต้องพิมพ์ซ้ำ
41. ในฐานะ Staff ฉันต้องการให้ออเดอร์เก็บสำเนาที่อยู่ของตัวเอง เพื่อให้การแก้ภายหลังไม่เปลี่ยนประวัติ

### การชำระเงิน

42. ในฐานะ Staff ฉันต้องการบันทึกวิธีจ่ายเงินสดหรือโอนและกดชำระแล้ว เพื่อให้ยอดวันนี้ตรงกับเงินจริง
43. ในฐานะ Staff ฉันต้องการให้ระบบบันทึกเวลาที่ชำระ เพื่อให้รายงานอยู่วันที่ถูกต้อง
44. ในฐานะ Staff ฉันต้องการบันทึกจำนวนเงินที่รับและเลขอ้างอิงการโอนแบบไม่บังคับ เพื่อมีหลักฐานโดยไม่เพิ่มภาระ
45. ในฐานะ Staff ฉันต้องการให้ระบบไม่คำนวณเงินทอน เพื่อไม่แสร้งว่าเป็นลิ้นชักเงินสด

### รายงาน

46. ในฐานะ Super Admin ฉันต้องการเห็นยอดขายรายวันตามวันที่ชำระ เพื่อให้ตรงกับเงินที่ได้รับ
47. ในฐานะ Super Admin ฉันต้องการดูรายการออเดอร์ของแต่ละวันและกรองตามสถานะ เพื่อตรวจงานย้อนหลัง
48. ในฐานะ Super Admin ฉันต้องการแยกออเดอร์ที่ยกเลิกและหมดอายุออกจากยอดขาย เพื่ออธิบายส่วนต่างได้

### เปิดและปิดร้าน

49. ในฐานะ Super Admin ฉันต้องการปิดรับออเดอร์ด้วยการกดครั้งเดียว เพื่อหยุดรับออเดอร์ชั่วคราว
50. ในฐานะ Super Admin ฉันต้องการให้ช่วงปิดร้านยังเก็บข้อความแต่ไม่จับคำ เพื่อลดภาระระบบและยังเห็นว่ามีอะไรเข้ามา
51. ในฐานะ Super Admin ฉันต้องการให้เปิดร้านแล้วกลับมาทำงานปกติทันที เพื่อไม่ต้องตั้งค่าอะไรเพิ่ม

### บัญชีและสิทธิ์

52. ในฐานะ Super Admin ฉันต้องการสร้างบัญชี Staff ล่วงหน้าด้วยอีเมลและให้เข้าสู่ระบบด้วย Google เพื่อให้เฉพาะคนของร้านเข้าได้
53. ในฐานะ Staff ฉันต้องการออกจากระบบแล้วให้ session ใช้ไม่ได้ เพื่อความปลอดภัยเมื่อทำมือถือหาย
54. ในฐานะ Super Admin ฉันต้องการระงับบัญชีพนักงานที่ลาออก โดยไม่ทำให้ประวัติออเดอร์หาย
55. ในฐานะ Super Admin ฉันต้องการกู้คืนบัญชี Super Admin ผ่านสคริปต์ เพื่อไม่ให้บัญชี Google ที่หายไปล็อกทั้งร้านออก

### ข้อมูล

56. ในฐานะ Super Admin ฉันต้องการให้ระบบลบข้อความดิบหลัง 45 วันและข้อมูลลูกค้าที่ไม่สั่ง 6 เดือน เพื่อปฏิบัติตาม PDPA
57. ในฐานะ Super Admin ฉันต้องการให้มี dump ฐานข้อมูลรายวัน เพื่อไม่ให้ประวัติออเดอร์หายถาวรเมื่อระบบมีปัญหา

## Implementation Decisions

### โมดูล

- **LINE Intake** — รับ webhook, ตรวจ `x-line-signature` จาก raw body, dedupe ด้วย `webhookEventId`, เก็บข้อความ, ตอบ 200
- **Term Matcher** — ฟังก์ชันบริสุทธิ์: รับพจนานุกรมคำที่ตั้งราคา + ข้อความ คืนรายการที่เสนอ (เมนู, ตัวเลือก, จำนวน, ราคา) พร้อมส่วนที่จับไม่ได้
- **Order Service** — สร้าง/รวม/ยืนยัน/ทิ้งออเดอร์ร่าง, เปลี่ยนสถานะ, ยกเลิก, บันทึกการชำระเงิน, ตั้งที่อยู่; ตรวจ version และสิทธิ์
- **Menu Admin** — เมนู, กลุ่มตัวเลือก, ค่าตัวเลือก, คำเรียก
- **Reporting** — ยอดขายรายวันและรายการออเดอร์
- **Auth Guard** — ตรวจ session ของ Supabase และบทบาทจากฐานข้อมูล (ไม่เชื่อ claim ใน JWT)

### สัญญา API (server route handlers)

| Endpoint | ผู้ใช้ | พฤติกรรม |
|---|---|---|
| `POST /api/line/webhook` | ไม่มี (ใช้ signature) | รับ event, dedupe, เก็บข้อความ, สร้าง draft ถ้าร้านเปิด |
| `GET /api/orders?date=&status=` | Staff | รายการออเดอร์ของวัน |
| `GET /api/inbox` | Staff | ข้อความที่ไม่ได้กลายเป็นออเดอร์ |
| `POST /api/orders` | Staff | สร้างออเดอร์เอง |
| `PATCH /api/orders/:id` | Staff | แก้รายการ/ที่อยู่ พร้อม `version` |
| `POST /api/orders/:id/confirm` | Staff | draft → Received พร้อม snapshot |
| `POST /api/orders/:id/transition` | Staff | เปลี่ยนสถานะตามตารางที่อนุญาต |
| `POST /api/orders/:id/cancel` | Staff / Super Admin | ยกเลิกตามกติกาและเหตุผล |
| `POST /api/orders/:id/payment` | Staff | ตั้งวิธีจ่าย/สถานะ/`paid_at` |
| `GET/POST/PATCH/DELETE /api/menus`, `/api/option-groups`, `/api/option-values`, `/api/priced-terms` | Super Admin | จัดการข้อมูลหลัก |
| `GET /api/reports/daily?date=` | Staff | ยอดขายและรายการของวัน |
| `POST /api/settings/store` | Super Admin | เปิด/ปิดรับออเดอร์ |

ความหมายของ error: `401` ไม่ได้ล็อกอิน, `403` ไม่มีสิทธิ์, `404` ไม่พบ, `409` version ไม่ตรงหรือ transition ไม่ได้รับอนุญาต, `422` ข้อมูลไม่ถูกต้อง

### ทางเดินข้อมูล

- ทุกการเขียนผ่าน route handler ฝั่งเซิร์ฟเวอร์ที่ตรวจสิทธิ์เอง; เบราว์เซอร์อ่านข้อมูลและ subscribe Realtime ผ่าน RLS
- Webhook ประมวลผลในคำขอเดียว (ไม่ใช้คิว) เพราะงานคือ insert + จับคำ + insert และไม่มี LINE call ขาออก; หากวัดแล้วเกินงบ 2 วินาทีให้เพิ่มคิวภายหลัง
- การเรียก LINE ขาออกมีเพียงดึงโปรไฟล์ผู้ใช้เมื่อพบลูกค้าใหม่; ถ้าล้มเหลวให้เก็บชื่อเป็นค่าว่างและทำงานต่อ

### ฐานข้อมูล

- ตารางตาม SRS ข้อ 6: `users`, `customers`, `messages`, `menus`, `option_groups`, `option_values`, `menu_option_groups`, `priced_terms`, `orders`, `order_items`, `order_status_history`, `payment`, `payment_history`, `settings`, `webhook_events`
- `webhook_event_id` เป็น primary key ของ `webhook_events`; insert ชนกัน = event ซ้ำ ให้ตอบ 200 โดยไม่ทำอะไร
- เงินเก็บเป็นจำนวนเต็มหน่วยสตางค์ เพื่อเลี่ยงเศษทศนิยม
- เวลาเก็บ `timestamptz`; ขอบวันคำนวณที่ Asia/Bangkok
- `orders.version` เพิ่มทุกครั้งที่เขียน; update ใช้เงื่อนไข `version = :expected` และคืน `409` เมื่อไม่มีแถวถูกแก้
- `order_number` รูปแบบ `YYMMDD-NNN` ต่อวัน ใช้ตัวนับในฐานข้อมูลและ unique constraint กันชน
- `priced_terms.term` unique หลัง normalize; เก็บรูป normalize ไว้ใช้จับคู่
- RLS เปิดบนทุกตารางที่ expose; role ของผู้ใช้อยู่ใน `users` และตรวจซ้ำที่เซิร์ฟเวอร์

### กติกาทางธุรกิจที่เข้ารหัสไว้

- สถานะ: `Draft → Received → Preparing → Delivering → Delivered`; `Cancelled` และ `Expired` เป็นปลายทาง; ห้ามย้อนทุกกรณี
- ยกเลิก: Staff ได้ถึง `Preparing`; หลัง `Delivering` เฉพาะ Super Admin และต้องมีเหตุผล
- ยอดขาย: ผลรวม `order_items.line_total` ของออเดอร์ที่ `payment.status = paid` และสถานะไม่ใช่ `Cancelled`/`Expired` จัดกลุ่มตามวันที่ของ `paid_at`
- ไม่มีการส่งข้อความออกจากระบบในทุกกรณี รวมถึงข้อความแจ้งสถานะ
- ร้านปิด: เก็บข้อความดิบ, ไม่จับคำ, ไม่สร้าง draft; เปิดแล้วกลับมาปกติ
- เก็บข้อมูล: ข้อความ 45 วัน, ลูกค้าที่ไม่สั่ง 6 เดือน, ออเดอร์และยอดขาย 1 ปี (งานลบรายวันผ่าน pg_cron)

### สิ่งที่ต้องมีนอกโค้ด

- โปรเจกต์ Supabase (region Singapore) + migration ผ่าน Supabase CLI
- Google OAuth client (Testing + test users) เชื่อมกับ Supabase Auth; ปิด signup
- Cloudflare Workers สำหรับ deploy; ตั้ง webhook URL ใน LINE console
- GitHub Actions รายวันสำหรับ `supabase db dump`

## Testing Decisions

### Seam

**Seam 1 — HTTP surface + order lifecycle (integration, Postgres จริง)**
ยิง `Request` เข้า route handler โดยตรง (ไม่ต้องเปิดพอร์ต) แล้วตรวจผลจากฐานข้อมูลจริง ครอบ: signature, dedupe, เก็บข้อความ, จับคำ, สร้าง/รวม draft, ยืนยัน, transition, ยกเลิก, การชำระเงิน, รายงาน และการตรวจสิทธิ์
- ไม่ mock Postgres และไม่ mock LINE (ไม่มี call ขาออก)
- session ใช้ JWT จริงที่ mint จาก secret ของ Supabase local
- webhook fixture เป็น payload ดิบที่เซ็นด้วย channel secret สำหรับเทส
- แต่ละเทสอยู่ใน transaction ที่ rollback

**Seam 2 — Term Matcher (pure function)**
`suggestItems(dictionary, text)` ทดสอบด้วย corpus ข้อความไทยจริง 100–200 ประโยค ครอบ alias, คำยาวสุดก่อน, การไม่นับซ้ำ, จำนวนทุกรูปแบบ, normalize, คำแปลก, และเคส "โกโก้ปั่น"

### หลักการ

- ทดสอบพฤติกรรมภายนอกเท่านั้น: เรียก endpoint หรือฟังก์ชันสาธารณะ แล้วตรวจผลที่ผู้ใช้เห็น (response, สถานะ, ยอดเงิน, แถวในฐานข้อมูล) — ไม่ตรวจสอบฟังก์ชันภายในหรือลำดับการเรียก
- ตั้งข้อมูลด้วย SQL fixture, กระทำผ่าน seam, ตรวจด้วย SQL หรือ response
- ข้อความในเทสใช้คำจาก `GLOSSARY.md` และชื่อเมนู/คำเรียกภาษาไทยจริง

### Stack

Vitest + local Supabase (`supabase start`) · corpus เก็บเป็นไฟล์ข้อมูลใน repo · ไม่ทำ UI automation ใน v1 (ยืนยันหน้าจอด้วยมือตาม acceptance criteria)

### Prior art

ไม่มี — repo นี้ยังเป็น scaffold ของ Next.js ไม่มีเทสใด ๆ มาก่อน

## Out of Scope

- การส่งข้อความใด ๆ ออกจากระบบ (reply, push, multicast, broadcast, แจ้งสถานะ)
- การสร้างออเดอร์อัตโนมัติโดยไม่มีการยืนยัน
- สต็อกวัตถุดิบ สมาชิก สะสมแต้ม โปรโมชั่น เครดิต
- Payment Gateway, การตรวจสลิป, เงินทอน, จ่ายบางส่วน, คืนเงิน, กระทบยอด
- หลายสาขา ค่าจัดส่งตามระยะทาง GPS ตารางเวร บัญชีและภาษีเต็มรูปแบบ
- Deep link ไปยังแชทลูกค้าใน LINE OA Manager (LINE ไม่รองรับ)
- AI API ที่มีค่าใช้จ่าย
- UI automation และ native mobile app
