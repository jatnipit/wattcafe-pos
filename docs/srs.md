# Software Requirements Specification — Watt Cafe POS

เวอร์ชัน: 2.0
วันที่: 30 ตุลาคม 2026
สถานะ: ใช้เป็นฐานสำหรับออกแบบและแตกงานพัฒนา
ธุรกิจ: ร้านกาแฟและน้ำปั่นร้านเดียวในหมู่บ้าน
รูปแบบระบบ: Web-based POS + LINE Official Account (รับข้อความเท่านั้น)
คำศัพท์: ใช้ตาม [`GLOSSARY.md`](../GLOSSARY.md)
การตัดสินใจสำคัญ: ดู [`docs/adr/`](./adr/)

## บันทึกการเปลี่ยนแปลงจากฉบับ 1.0

- ตัดการสร้างออเดอร์อัตโนมัติและแนวคิด `Confidence` ทั้งหมด — ร้านยืนยันทุกออเดอร์
- ตัดการส่งข้อความออกจากระบบทั้งหมด (reply และ push) — ร้านพิมพ์ตอบเองผ่าน LINE OA Manager
- ตัดการติดตามการเงินเชิงลึก (เงินคืน กระทบยอด ตรวจสลิป)
- ที่อยู่จัดส่งกรอกโดยร้าน ไม่แกะจากข้อความ
- เพิ่มการล็อกอินด้วย Google, การจำกัดบัญชีล่วงหน้า และนโยบายปิดร้านแบบไม่ประมวลผลข้อความ
- ระบุระยะเวลาเก็บข้อมูลและโควตาของผู้ให้บริการไว้ชัดเจน

## 1. บทนำ

### 1.1 วัตถุประสงค์

ระบบรับข้อความสั่งซื้อของลูกค้าจาก LINE Official Account มาแสดงบนกระดานออเดอร์ พร้อมจับคำที่ร้านตั้งราคาไว้เพื่อเสนอรายการและยอดเงิน ให้ร้านตรวจ แก้ไข และยืนยันก่อนเริ่มทำ

ระบบต้องลดงานพิมพ์ซ้ำของร้าน โดยไม่ตัดสินใจแทนร้านในจุดที่ผิดแล้วเสียหาย และต้องไม่สร้างค่าใช้จ่ายรายเดือนจากการส่งข้อความ

### 1.2 เป้าหมาย

1. ข้อความจากลูกค้าทุกข้อความปรากฏในระบบโดยไม่ต้องคัดลอกด้วยมือ
2. ร้านเห็นข้อความต้นฉบับเทียบกับรายการที่ระบบเสนอได้ในหน้าเดียว
3. ร้านแก้เมนู จำนวน ตัวเลือก และราคาได้ก่อนยืนยัน
4. ร้านติดตามสถานะออเดอร์ได้ครบวงจรและตรวจย้อนหลังได้
5. ค่าใช้จ่ายด้านโครงสร้างพื้นฐานและข้อความเป็นศูนย์ในระยะเริ่มต้น

### 1.3 คำนิยาม

ใช้คำตาม `GLOSSARY.md` ทั้งหมด โดยคำหลักคือ Menu Item, Option Group, Option Value, Priced Term, Draft Order, Inbox Message, Order, Revenue

## 2. ขอบเขต

### 2.1 อยู่ในขอบเขต

- รับ webhook จาก LINE Messaging API และเก็บข้อความ
- จับคำที่ตั้งราคาจากข้อความและสร้างออเดอร์ร่าง
- กระดานออเดอร์สำหรับตรวจ แก้ไข และยืนยัน
- จัดการเมนู กลุ่มตัวเลือก ค่าตัวเลือก และคำเรียก
- จัดการสถานะออเดอร์และประวัติ
- จัดเก็บข้อมูลลูกค้าและที่อยู่ล่าสุดที่ร้านบันทึก
- บันทึกวิธีและสถานะการชำระเงินที่ร้านกดเอง
- เปิด/ปิดรับออเดอร์
- รายงานยอดขายและรายการออเดอร์รายวัน
- บัญชีผู้ใช้และสิทธิ์สองระดับ
- การสำรองข้อมูลรายวัน

### 2.2 ไม่อยู่ในขอบเขต

- การส่งข้อความใด ๆ ออกจากระบบ (reply, push, multicast, broadcast, แจ้งสถานะอัตโนมัติ)
- การสร้างออเดอร์อัตโนมัติโดยไม่มีการยืนยันของร้าน
- การจัดการสต็อกวัตถุดิบ
- ระบบสมาชิก สะสมแต้ม โปรโมชั่น เครดิต
- Payment Gateway การตรวจสลิป การคำนวณเงินทอน การจ่ายบางส่วน การคืนเงิน
- การติดตามสถานะการเงินหรือกระทบยอดใด ๆ
- หลายสาขา หลายร้าน ค่าจัดส่งตามระยะทาง GPS ตารางเวร
- บัญชีและภาษีเต็มรูปแบบ
- Deep link ไปยังแชทของลูกค้ารายใดรายหนึ่งใน LINE OA Manager (LINE ไม่รองรับ)
- AI API ที่มีค่าใช้จ่าย

## 3. ผู้ใช้และสิทธิ์

### 3.1 Staff

บัญชีของตนเอง ทำงานประจำวัน: ดูข้อความและออเดอร์ ตรวจแก้และยืนยันออเดอร์ เปลี่ยนสถานะ บันทึกการชำระเงิน สร้างออเดอร์เอง ดูรายงาน

### 3.2 Super Admin

มีบัญชีเดียวในระบบ มีสิทธิ์ทั้งหมดของ Staff และจัดการเมนู ตัวเลือก คำเรียก บัญชีผู้ใช้ การตั้งค่าร้าน และการเปิด/ปิดรับออเดอร์

### 3.3 กฎการกำหนดสิทธิ์

- บทบาทเก็บในฐานข้อมูลและตรวจที่เซิร์ฟเวอร์ทุกครั้ง (FR-067)
- ผู้ใช้เปลี่ยนบทบาทตนเองไม่ได้ และสร้าง Super Admin เพิ่มจากหน้าจอไม่ได้
- การระงับบัญชีต้องไม่ทำให้ข้อมูลออเดอร์และประวัติหาย
- บัญชี Super Admin คนแรกสร้างตอนติดตั้ง และกู้คืนด้วยสคริปต์ที่ใช้ service key เท่านั้น

## 4. Functional Requirements

### 4.1 การรับข้อความจาก LINE

- **FR-001** ระบบต้องรับ webhook ผ่าน HTTPS ที่ URL คงที่
- **FR-002** ระบบต้องตรวจ `x-line-signature` จาก raw body ก่อนประมวลผล และไม่ประมวลผลเมื่อตรวจไม่ผ่าน
- **FR-003** ระบบต้องกันการประมวลผลซ้ำด้วย `webhookEventId` และต้องไม่สร้างผลข้างเคียงซ้ำเมื่อ event เดิมมาอีก
- **FR-004** ระบบต้องตอบ `200` ภายใน 2 วินาที และทำงานที่ใช้เวลานานกว่านั้นนอกเส้นทางตอบกลับ
- **FR-005** ระบบต้องระบุลูกค้าด้วย LINE user ID และบันทึกชื่อที่แสดงจาก LINE profile
- **FR-006** ระบบต้องไม่ส่งข้อความใด ๆ ออกไปหาลูกค้าไม่ว่ากรณีใด
- **FR-007** ระบบต้องบันทึกข้อความดิบ เวลาที่รับ และผู้ส่ง ทุกข้อความที่มาถึง แม้ร้านจะปิดรับออเดอร์
- **FR-008** ระบบต้องบันทึกข้อผิดพลาดที่ทำให้ประมวลผลไม่สำเร็จ และต้องไม่ทิ้งข้อความโดยไม่มีร่องรอย

### 4.2 การจับคำและการสร้างออเดอร์ร่าง

- **FR-009** ระบบต้องจับ `Priced Term` จากข้อความและสร้างรายการที่เสนอพร้อมราคา
- **FR-010** ระบบต้องใช้เฉพาะเมนูและค่าตัวเลือกที่เปิดใช้งานอยู่ในปัจจุบัน
- **FR-011** ระบบต้อง normalize ข้อความก่อนจับคำ: ตัดช่องว่างส่วนเกิน ไม่สนตัวพิมพ์ ตัดคำลงท้าย ครับ/ค่ะ/นะ/จ้า และแปลงเลขไทยเป็นเลขอารบิก
- **FR-012** ระบบต้องจับคำที่ยาวที่สุดก่อน และต้องไม่นับคำที่ทับซ้อนกันสองครั้ง
- **FR-013** ระบบต้องรองรับจำนวนในรูปแบบ `2`, `2 แก้ว`, `x2`, `สองแก้ว` และเลขไทย
- **FR-014** เมื่อจับคำได้อย่างน้อยหนึ่งคำ ระบบต้องสร้าง Draft Order ที่เก็บข้อความต้นฉบับและรายการที่เสนอ
- **FR-015** เมื่อจับคำไม่ได้เลย ระบบต้องไม่สร้างออเดอร์ และเก็บข้อความเป็น Inbox Message
- **FR-016** ข้อความใหม่จากลูกค้ารายเดิมภายใน 10 นาที ต้องถูกรวมเข้า Draft Order เดิมที่ยังไม่ถูกยืนยัน
- **FR-017** ระบบต้องไม่เดาคำที่ไม่รู้จัก ไม่เดาจำนวน และไม่ยืนยันออเดอร์แทนร้าน
- **FR-018** Draft Order ที่ไม่ถูกยืนยันเกิน 24 ชั่วโมง ต้องถูกปิดเป็น `Expired` และไม่ถูกนับเป็นยอดขาย

### 4.3 การยืนยันและแก้ไขออเดอร์

- **FR-019** หน้าจอออเดอร์ร่างต้องแสดงข้อความต้นฉบับเต็มของลูกค้า
- **FR-020** ร้านต้องแก้เมนู จำนวน ตัวเลือก และราคาของแต่ละรายการได้ก่อนยืนยัน
- **FR-021** การยืนยันต้องเปลี่ยนสถานะเป็น `Received` และบันทึก snapshot ชื่อเมนู ตัวเลือก และราคา ณ ขณะนั้น
- **FR-022** ระบบต้องคำนวณยอดรวมจากรายการที่ร้านยืนยัน
- **FR-023** การแก้ราคาบนออเดอร์ต้องไม่เปลี่ยนราคาเมนูต้นแบบ
- **FR-024** การแก้ไขออเดอร์ต้องตรวจ version ก่อนบันทึก และแจ้งเมื่อมีผู้ใช้อื่นแก้ก่อน
- **FR-025** Staff และ Super Admin ต้องสร้างออเดอร์ด้วยตนเองได้เสมอ แม้ไม่มีข้อความหรือร้านปิดรับออเดอร์
- **FR-026** ร้านต้องทิ้ง Draft Order ได้ โดยไม่ถูกนับเป็นออเดอร์หรือยอดขาย

### 4.4 เมนู ตัวเลือก และคำเรียก

- **FR-027** Super Admin ต้องเพิ่ม แก้ไข และลบเมนูได้ โดยเมนูที่ถูกอ้างในออเดอร์ต้องไม่ทำให้ประวัติเสียหาย
- **FR-028** เมนูต้องมีชื่อ ราคาฐาน และสถานะเปิดขาย
- **FR-029** กลุ่มตัวเลือกต้องนิยามครั้งเดียวและใช้ร่วมกับหลายเมนูได้
- **FR-030** กลุ่มตัวเลือกต้องกำหนดได้ว่าบังคับเลือกหรือไม่ และเลือกได้กี่ค่า (ต่ำสุด–สูงสุด)
- **FR-031** ค่าตัวเลือกต้องมีราคาบวกที่อาจเป็นศูนย์ และผูกกับกลุ่มของตน
- **FR-032** คำเรียกต้องผูกกับเมนูหนึ่งรายการหรือค่าตัวเลือกหนึ่งค่า และต้องไม่ซ้ำกับคำอื่นทั้งระบบ
- **FR-033** Super Admin เท่านั้นที่เพิ่ม แก้ และลบคำเรียกได้
- **FR-034** Super Admin ต้องปิดเมนูที่ขายไม่ได้ทันที โดยไม่กระทบออเดอร์เก่า
- **FR-035** เมนูที่ปิดขายต้องไม่ถูกจับเป็นรายการใหม่ในออเดอร์ร่าง
- **FR-036** ราคารวมของรายการต้องคำนวณจากราคาเมนูบวกค่าตัวเลือกที่เลือก

### 4.5 สถานะออเดอร์

- **FR-037** สถานะที่ใช้คือ `Draft`, `Received`, `Preparing`, `Delivering`, `Delivered`, `Cancelled`, `Expired`
- **FR-038** การเปลี่ยนสถานะต้องเป็นไปตามลำดับ `Draft → Received → Preparing → Delivering → Delivered` เท่านั้น
- **FR-039** ระบบต้องไม่อนุญาตให้ย้อนสถานะทุกกรณี การแก้ที่ผิดต้องทำด้วยการยกเลิกและสร้างใหม่
- **FR-040** ทุกการเปลี่ยนสถานะต้องบันทึกผู้ทำ เวลา และสถานะก่อน–หลัง
- **FR-041** Staff ยกเลิกได้ถึงสถานะ `Preparing`; หลัง `Delivering` ต้องเป็น Super Admin และต้องระบุเหตุผล
- **FR-042** `Delivered`, `Cancelled`, `Expired` เป็นสถานะสุดท้าย
- **FR-043** กระดานออเดอร์ต้องแสดงสถานะล่าสุดและเวลาที่เปลี่ยน
- **FR-044** กระดานออเดอร์ต้องอัปเดตอัตโนมัติด้วย Realtime และมี fallback เป็นการดึงข้อมูลทุก 30 วินาทีเมื่อการเชื่อมต่อหลุด

### 4.6 ลูกค้าและที่อยู่

- **FR-045** ระบบต้องเชื่อมโยงลูกค้ากับ LINE user ID และไม่สร้างลูกค้าซ้ำจาก user เดียวกัน
- **FR-046** ร้านต้องกรอกบ้านเลขที่และรายละเอียดที่อยู่บนหน้าจอออเดอร์ได้
- **FR-047** ที่อยู่ที่กรอกต้องถูกบันทึกเป็นที่อยู่ล่าสุดของลูกค้า และเก็บสำเนาลงออเดอร์
- **FR-048** เมื่อสร้างออเดอร์ให้ลูกค้ารายเดิม ระบบต้องแสดงที่อยู่ล่าสุดให้เป็นค่าเริ่มต้น
- **FR-049** ระบบต้องไม่แกะที่อยู่จากข้อความของลูกค้าโดยอัตโนมัติ
- **FR-050** การแก้ที่อยู่ในอนาคตต้องไม่เปลี่ยนสำเนาที่อยู่ในออเดอร์เก่า

### 4.7 การชำระเงินและยอดขาย

- **FR-051** วิธีชำระเงินต้องรองรับอย่างน้อยเงินสดและโอน/QR พร้อมเพย์
- **FR-052** สถานะการชำระเงินมีสองค่า: ยังไม่ชำระ และชำระแล้ว พร้อมบันทึก `paid_at`
- **FR-053** ร้านเท่านั้นที่เปลี่ยนสถานะการชำระเงินได้ และทุกการเปลี่ยนต้องมีประวัติ
- **FR-054** ระบบต้องเก็บจำนวนเงินที่รับและเลขอ้างอิงการโอนแบบไม่บังคับ
- **FR-055** ระบบต้องไม่คำนวณเงินทอนและไม่รองรับการจ่ายบางส่วน
- **FR-056** ระบบต้องไม่ตรวจสลิป ไม่กระทบยอด และไม่มีแนวคิดการคืนเงิน
- **FR-057** ยอดขายคือผลรวมของออเดอร์ที่ชำระแล้วและไม่ถูกยกเลิกหรือหมดอายุ โดยนับตามวันที่ `paid_at` ในเขตเวลา Asia/Bangkok
- **FR-058** ออเดอร์ที่ยังไม่ชำระ ยกเลิก หรือหมดอายุ ต้องไม่ถูกนับเป็นยอดขาย

### 4.8 เปิดและปิดรับออเดอร์

- **FR-059** Super Admin ต้องเปิดและปิดรับออเดอร์ได้จากหน้าจอ POS
- **FR-060** เมื่อปิดรับออเดอร์ ระบบต้องยังเก็บข้อความดิบ แต่ต้องไม่จับคำและไม่สร้าง Draft Order
- **FR-061** การปิดรับออเดอร์ต้องไม่ลบหรือเปลี่ยนสถานะออเดอร์ที่มีอยู่
- **FR-062** เมื่อเปิดรับออเดอร์อีกครั้ง ระบบต้องกลับมาจับคำและสร้าง Draft Order ตามปกติ
- **FR-063** Staff และ Super Admin ต้องสร้างออเดอร์ด้วยตนเองได้ตลอดเวลา

### 4.9 รายงานและประวัติ

- **FR-064** ระบบต้องแสดงยอดขายรายวันตามนิยามใน FR-057
- **FR-065** ระบบต้องแสดงรายการออเดอร์ของแต่ละวัน พร้อมกรองตามวันที่และสถานะ
- **FR-066** รายงานต้องแสดงอย่างน้อย เลขที่ออเดอร์ เวลาสั่ง เวลาชำระ รายการ ยอดรวม สถานะ วิธีชำระ และสถานะชำระ
- **FR-067** รายงานต้องแยกออเดอร์ที่ยืนยันแล้ว ออเดอร์ร่าง ออเดอร์ที่ยกเลิก และที่หมดอายุ
- **FR-068** การแก้เมนูหรือราคาในปัจจุบันต้องไม่เปลี่ยนยอดของออเดอร์เก่า
- **FR-069** การเปลี่ยนสถานะและการเปลี่ยนสถานะการชำระเงินต้องตรวจย้อนหลังได้ว่าใครทำเมื่อไร

### 4.10 บัญชีผู้ใช้

- **FR-070** ระบบต้องรองรับการเข้าสู่ระบบด้วย Google ผ่าน Supabase Auth
- **FR-071** ระบบต้องปิดการสมัครใหม่ และยอมให้เฉพาะบัญชีที่ Super Admin สร้างล่วงหน้าด้วยอีเมลเท่านั้น
- **FR-072** Super Admin ต้องสร้าง แก้ไข ระงับ และเปิดบัญชี Staff ได้
- **FR-073** ระบบต้องตรวจสิทธิ์ที่เซิร์ฟเวอร์สำหรับทุกการกระทำที่มีข้อจำกัด
- **FR-074** การออกจากระบบต้องทำให้ session ที่ออกไปแล้วใช้ไม่ได้
- **FR-075** ระบบต้องปฏิเสธผู้ใช้ที่ล็อกอินสำเร็จแต่ไม่มีสิทธิ์ในระบบ พร้อมข้อความที่ไม่อธิบายรายละเอียดภายใน

## 5. Workflow หลัก

### 5.1 รับออเดอร์จาก LINE

1. ลูกค้าส่งข้อความถึง OA
2. LINE ส่ง webhook; ระบบตรวจ signature และ dedupe
3. ระบบตอบ 200 แล้วเก็บข้อความและดึงชื่อผู้ส่ง
4. ถ้าร้านเปิด: ระบบ normalize และจับคำที่ตั้งราคา
5. จับได้อย่างน้อยหนึ่งคำ → สร้าง Draft Order และแสดงบนกระดานพร้อมข้อความต้นฉบับ
6. จับไม่ได้ → เก็บเป็น Inbox Message ให้ร้านเปิดดู
7. ร้านตรวจ แก้เมนู จำนวน ตัวเลือก ราคา และที่อยู่
8. ร้านกดยืนยัน → `Received` พร้อม snapshot
9. ร้านทำเครื่องดื่ม (`Preparing`) → ส่ง (`Delivering`) → ยืนยันถึงมือ (`Delivered`)
10. ร้านบันทึกวิธีชำระและกดชำระแล้วเมื่อได้รับเงิน
11. ร้านพิมพ์ตอบลูกค้าผ่าน LINE OA Manager เอง

### 5.2 ร้านปิดรับออเดอร์

1. ลูกค้าส่งข้อความ
2. ระบบเก็บข้อความดิบและตอบ 200 แต่ไม่จับคำและไม่สร้าง Draft Order
3. ร้านเห็นข้อความในแอป LINE ตามปกติ
4. หากรับเป็นกรณีพิเศษ ร้านสร้างออเดอร์เองจากหน้าจอ POS
5. เมื่อเปิดร้าน ข้อความใหม่กลับเข้าสู่ขั้นตอนปกติ

### 5.3 แก้ออเดอร์ที่มีคนแก้พร้อมกัน

1. Staff A เปิดออเดอร์ ระบบส่ง version มาด้วย
2. Staff B เปิดออเดอร์เดียวกันและบันทึกก่อน
3. การบันทึกของ A ถูกปฏิเสธเพราะ version ไม่ตรง
4. ระบบแจ้งว่า "ออเดอร์นี้ถูกแก้โดยคนอื่น" และโหลดข้อมูลล่าสุดให้ตรวจใหม่

### 5.4 ลูกค้าเดิมสั่งโดยไม่ระบุที่อยู่

1. ระบบจับคำและสร้าง Draft Order
2. ระบบเติมที่อยู่ล่าสุดของลูกค้ารายนั้นเป็นค่าเริ่มต้น
3. ร้านตรวจและแก้ได้ ก่อนยืนยัน
4. ที่อยู่ที่ยืนยันแล้วถูกเก็บเป็นสำเนาในออเดอร์

## 6. ข้อกำหนดด้านข้อมูล

เวลาเก็บเป็น `timestamptz` (UTC) และแสดงผลเป็น Asia/Bangkok

|---|---|
| users | id, supabase_user_id, email, display_name, role, status, created_at |
| customers | id, line_user_id, display_name, latest_address, last_order_at, created_at |

| menus | id, name, base_price, is_available, created_at, updated_at |
| option_groups | id, name, is_required, min_select, max_select |
| option_values | id, option_group_id, name, additional_price, is_active |
| menu_option_groups | menu_id, option_group_id, price_override |
| priced_terms | id, term, menu_id, option_value_id, created_at |
| orders | id, order_number, customer_id, status, source, version, note, created_at, confirmed_at, delivered_at, cancelled_at, cancelled_reason, expired_at |
| order_items | id, order_id, menu_id, menu_name_snapshot, quantity, unit_price_snapshot, options_snapshot, line_total |

ข้อกำหนดเพิ่มเติม:

- ออเดอร์เก็บ snapshot ชื่อ ราคา และตัวเลือก เพื่อไม่ให้การแก้เมนูภายหลังเปลี่ยนประวัติ
- `priced_terms.term` ต้อง unique หลัง normalize
- ไม่เก็บรหัสผ่านในระบบ เพราะใช้ Google เป็นผู้ยืนยันตัวตน
- ความลับ (channel secret, access token, service key) เก็บใน environment ของผู้ให้บริการเท่านั้น

## 7. Non-functional Requirements

### 7.1 การใช้งาน

- **NFR-001** หน้าจอ POS ต้องใช้ได้บนโทรศัพท์และแท็บเล็ต
- **NFR-002** กระดานออเดอร์ต้องอ่านง่ายและกดเปลี่ยนสถานะได้ในหนึ่งครั้ง
- **NFR-003** การยืนยันออเดอร์ต้องไม่ต้องกรอกข้อมูลซ้ำที่มีอยู่แล้ว

### 7.2 ความปลอดภัย

- **NFR-004** การสื่อสารทั้งหมดใน production ต้องเป็น HTTPS
- **NFR-005** ต้องตรวจ LINE signature ทุกครั้ง และไม่ไว้ใจข้อมูลจาก client
- **NFR-006** ต้องตรวจสิทธิ์ที่เซิร์ฟเวอร์ก่อนเข้าถึงข้อมูลทุกครั้ง
- **NFR-007** service role key และ channel secret ต้องไม่ปรากฏในฝั่ง client
- **NFR-008** ต้องเปิด RLS บนตารางที่ expose และไม่พึ่งการซ่อนปุ่มบนหน้าเว็บ

### 7.3 ความน่าเชื่อถือ

- **NFR-009** ต้องกันออเดอร์ซ้ำจาก webhook ที่ส่งซ้ำ
- **NFR-010** ต้องบันทึกข้อผิดพลาดจาก LINE และจากฐานข้อมูลเพื่อตรวจย้อนหลัง
- **NFR-011** การเปลี่ยนสถานะต้องไม่ทำให้ข้อมูลขัดแย้งกัน แม้มีผู้ใช้หลายคน
- **NFR-012** ต้องมี `db dump` อัตโนมัติรายวันเก็บไว้นอกระบบ เนื่องจากแผนฟรีไม่มี backup

### 7.4 ประสิทธิภาพ

- **NFR-013** กระดานออเดอร์ต้องแสดงผลภายใน 3 วินาทีในสภาวะปกติ
- **NFR-014** ต้องตอบ webhook ภายใน 2 วินาที
- **NFR-015** ต้องอยู่ในเพดาน Cloudflare Workers free: CPU 10 ms ต่อ request และ 100,000 request ต่อวัน; หากเกินให้พิจารณาอัปเกรดเป็น Workers Paid

### 7.5 การบำรุงรักษา

- **NFR-016** ต้องแยกส่วนรับ webhook, การจับคำ, การจัดการออเดอร์ และส่วนแสดงผลออกจากกัน
- **NFR-017** การเพิ่มเมนู ตัวเลือก และคำเรียกต้องไม่ต้องแก้โค้ด
- **NFR-018** โค้ดที่รันบน edge ต้องเล็ก เพราะข้อจำกัด CPU

### 7.6 ความเป็นส่วนตัว

- **NFR-019** เก็บออเดอร์และยอดขาย 1 ปี, ข้อความดิบ 45 วัน, ข้อมูลลูกค้า 6 เดือนหลังไม่มีการสั่ง
- **NFR-020** ต้องมีประกาศความเป็นส่วนตัวที่ระบุวัตถุประสงค์ ฐานทางกฎหมาย ประเภทข้อมูล ระยะเวลาเก็บ และสิทธิของเจ้าของข้อมูล ตาม PDPA
- **NFR-021** เก็บข้อมูลลูกค้าเท่าที่จำเป็นต่อการรับออเดอร์และจัดส่ง

## 8. Acceptance Criteria

1. ลูกค้าส่ง "โกโก้ปั่น 2 แก้ว" แล้วระบบสร้าง Draft Order ที่มีโกโก้ 35 + ปั่น 5 × 2 = 80 และแสดงข้อความต้นฉบับ
2. ร้านแก้ราคาบนออเดอร์แล้วยืนยัน ยอดรวมเปลี่ยนตามที่แก้ และเมนูต้นแบบไม่เปลี่ยน
3. ลูกค้าส่ง "สวัสดีครับ" แล้วระบบไม่สร้างออเดอร์ แต่ข้อความปรากฏใน Inbox Message
4. ข้อความเดิมถูกส่งซ้ำโดย LINE แล้วไม่เกิดออเดอร์หรือรายการซ้ำ
5. ร้านปิดรับออเดอร์แล้วลูกค้าส่งข้อความ ระบบเก็บข้อความแต่ไม่สร้าง Draft Order
6. ร้านเปิดรับออเดอร์อีกครั้ง ข้อความใหม่ถูกจับคำและสร้าง Draft Order ตามปกติ
7. Staff ยกเลิกออเดอร์ที่ `Preparing` ได้ แต่ยกเลิกที่ `Delivering` ไม่ได้
8. การเปลี่ยนสถานะย้อนกลับถูกปฏิเสธทุกกรณี
9. Staff สองคนแก้ Draft เดียวกัน คนที่บันทึกทีหลังได้รับแจ้งว่ามีคนแก้ก่อนและข้อมูลไม่ถูกทับ
10. ลูกค้าเดิมสั่งใหม่ ระบบเติมที่อยู่ล่าสุดให้ และร้านแก้ได้
11. ออเดอร์ที่ยังไม่ชำระไม่ถูกนับเป็นยอดขาย แม้จะ `Delivered` แล้ว
12. ออเดอร์ที่ชำระวันอังคารแต่ส่งวันจันทร์ ถูกนับเป็นยอดขายวันอังคาร
13. ออเดอร์ที่ยกเลิกหลังชำระแล้วหายจากยอดขายโดยไม่ต้องบันทึกการคืนเงิน
14. Staff ไม่สามารถเพิ่มเมนูหรือคำเรียก หรือจัดการบัญชีผู้ใช้ได้
15. ผู้ใช้ที่ล็อกอินด้วย Google แต่ไม่มีบัญชีในระบบถูกปฏิเสธ
16. ระบบไม่ส่งข้อความใด ๆ ออกไปหาลูกค้าในทุกกรณีทดสอบ

## 9. สมมติฐานและข้อจำกัด

- ร้านเดียว พื้นที่ส่งในหมู่บ้าน ไม่มีค่าจัดส่ง
- ลูกค้าสื่อสารผ่าน LINE OA เป็นหลัก และร้านตอบด้วยมือ
- ร้านจัดการเมนูเอง และยอมรับว่าข้อความที่พิมพ์ผิดจะถูกแก้ตอนยืนยัน
- ใช้แผนฟรีของ Supabase และ Cloudflare Workers; ยอมรับว่าไม่มี backup อัตโนมัติจนกว่าจะอัปเกรด
- แผนฟรีของ Supabase ไม่รองรับ session timeout อัตโนมัติ
- Next.js บน Cloudflare Workers ยังเป็น beta; หากมีปัญหาจะพิจารณา Workers Paid หรือย้ายผู้ให้บริการ
- ระบบไม่ใช่ระบบบัญชี และไม่ใช้เป็นหลักฐานทางภาษีโดยตรง

## 11. แนวทางสถาปัตยกรรมเบื้องต้น

- **LINE Intake** — ตรวจ signature, dedupe, เก็บข้อความ, ตอบ 200 เร็ว
- **Term Matcher** — normalize และจับคำจากพจนานุกรมที่สร้างจากเมนูและตัวเลือก
- **Order Service** — สร้าง draft, ยืนยัน, เปลี่ยนสถานะ, ตรวจ version
- **POS Web App** — กระดานออเดอร์ หน้าจอจัดการเมนู ผู้ใช้ และรายงาน (อ่านข้อมูลผ่าน RLS จากเบราว์เซอร์เมื่อเหมาะสม)
- **Database** — Postgres บน Supabase พร้อม RLS และ migration ผ่าน Supabase CLI
- **Auth** — Supabase Auth + Google, จำกัดด้วยบัญชีที่สร้างล่วงหน้า
- **Backup** — GitHub Actions รัน `supabase db dump` รายวัน

ไม่ใช้ microservices และไม่ใช้ AI API

## 12. ประเด็นที่ยังเปิดอยู่

- จะอัปเกรดเป็น Cloudflare Workers Paid หรือย้ายผู้ให้บริการ หากชนเพดาน CPU 10 ms
- จะเปิด Supabase Pro เพื่อให้มี backup อัตโนมัติหรือคงใช้ `db dump` เอง
- จะเพิ่มการแจ้งเตือนลูกค้าอัตโนมัติในอนาคตหรือไม่ (ต้องแลกกับค่าใช้จ่าย LINE)
